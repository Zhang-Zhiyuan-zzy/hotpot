# Open Babel Wrappers

## Introduction

`hotpot.cheminfo.obWrappers` is a small, auditable rule layer around selected
Open Babel operations. It addresses narrowly identified backend pathologies
without replacing Open Babel and without changing Hotpot's public force-field
interfaces.

The package separates three responsibilities:

1. a C++17 rule planner examines immutable atom, bond, and coordinate
   snapshots and returns an explicit mutation plan;
2. a Python bridge applies that plan to the Open Babel SWIG object;
3. the original `OBBuilder` or `OBForceField` performs the actual chemistry
   operation.

If no registered rule matches, the bridge delegates once to the native Open
Babel operation and does not change the molecule. Every applied rule is
reported with a stable ID, version, stage, priority, target atoms, metric, and
explicit mutations.

This package currently handles:

- a reproducible `OBBuilder` geometry defect for a narrowly defined neutral,
  tetracoordinate P(V) environment; and
- a numerical preflight for exactly or nearly collinear, non-linear centers
  that can make UFF proper-torsion gradients non-finite.

It does **not** modify the UFF energy or gradient formula, implement a new force
field, judge chemical reasonableness, or address metal relocation. In
particular, the Eu--N collapse observed in benchmark case 109 is outside this
package's scope and belongs to the complex coordination workflow.

## Design boundary

### Why a C++ planner and a Python SWIG bridge?

Open Babel's Python objects are generated by SWIG. Passing the undocumented
pointer stored in `OBMol.this` into an unrelated pybind11 module would couple
Hotpot to SWIG internals, object ownership, and the exact Open Babel C++ ABI.
Open Babel 3.1 and 3.2 also use different shared-library ABIs.

The native `_ob_rules` extension therefore has no Open Babel C++ dependency.
It consumes plain value snapshots and returns plain mutation records. The
Python bridge is the only layer that reads or mutates an `OBMol`. This design:

- avoids sharing C++ object pointers between SWIG and pybind11;
- avoids loading a second Open Babel shared library;
- keeps one native rules implementation across supported Open Babel versions;
- preserves the native Open Babel path for non-matching molecules; and
- makes every exceptional mutation observable and testable.

### Why not subclass, fork, or patch Open Babel?

| Approach | Decision | Reason |
|---|---|---|
| Composition used here | Adopted | Local, reversible, versioned, and does not change the public force-field API |
| Subclass `OBBuilder`/`OBForceField` | Rejected | The required internal operations are not stable extension hooks; it would depend on protected implementation details and ABI behavior |
| Maintain an Open Babel fork | Rejected for this package | It could alter the UFF derivative directly, but creates a large upgrade, binary-distribution, and validation burden |
| Patch Open Babel upstream | Complementary | Appropriate for the singular derivative itself, but cannot immediately protect users of already released Open Babel versions |

The collinearity rule prevents a known singular input and verifies the resulting
backend state. It must not be described as a correction to the UFF formula.

## Execution flow

### Coordinate building

```text
forcefields.backend._ob_build(mol)
  -> mol2obmol(mol)
  -> obWrappers.build(obmol, builder=OBBuilder())
       -> snapshot atoms and bonds
       -> _ob_rules.plan_build(...)
       -> no match: OBBuilder.Build(obmol) once
       -> match:
            apply temporary hybridization changes
            OBBuilder.Build(obmol) once
            restore hybridization in finally
  -> copy coordinates back to the Hotpot Molecule
```

### Force-field setup and optimization

```text
forcefields.backend._setup_forcefield_backend(...)
  -> obWrappers.prepare_optimization(obmol, effective_forcefield)
       -> non-UFF: strict no-op
       -> UFF:
            snapshot atoms, bonds, and coordinates
            _ob_rules.plan_optimization(...)
            apply deterministic coordinate changes
  -> OBForceField.Setup(obmol, constraints)
  -> if a rule was applied:
       validate_forcefield_state(backend, obmol)
       reject non-finite energy or gradients
  -> native steepest-descent or conjugate-gradient execution
```

Both the short candidate optimizer and the stateful epoch optimizer use the
same setup function, so the preflight covers ligand warmup, ring untangling,
coordination restoration, ordinary optimization, and complex optimization.

## Registry contract

A native rule is defined by:

```cpp
using RuleCondition = bool (*)(
    const MoleculeSnapshot&,
    const RuleParameters&
);

using RuleAction = void (*)(
    MoleculeSnapshot&,
    const RuleParameters&,
    const RuleDescriptor&,
    RulePlan&
);

struct RuleDefinition {
    RuleDescriptor descriptor;
    RuleCondition condition;
    RuleAction action;
};
```

The condition only decides whether its action should run. The action operates
on the planner's private snapshot and appends explicit changes to `RulePlan`.
It does not invoke Open Babel, select a workflow branch, accept a chemical
structure, or suppress a failure.

Rules are registered at native-module initialization with `RuleRegistrar`.
They execute deterministically in ascending order of:

```text
(stage, priority, rule_id, version)
```

Within one plan, later rules see the snapshot changes made by earlier rules.
Duplicate `(stage, rule_id)` registrations are rejected. At most 256 rule
applications may be emitted by one plan. The Python API intentionally exposes
only read access to the registry.

### Adding a compiled rule

1. Choose exactly one existing `RuleStage`, or add a new stage to both the C++
   and Python enums if a genuinely new lifecycle boundary is required.
2. Add a focused C++ source under `_native/` with a pure condition and action.
3. Give the rule a stable semantic `rule_id`, version, stage, and priority.
4. Register it with a translation-unit-local `const RuleRegistrar`.
5. Add the new source file to the `_ob_rules` extension in `setup.py`.
6. Add native boundary tests for positive matches, every intended exclusion,
   deterministic output, and interaction ordering.
7. Add bridge tests proving temporary mutations are restored and non-matching
   inputs use native Open Babel exactly once.
8. Add a real force-field integration test and the applicable benchmark before
   enabling the rule by default.

Do not register a broad fallback rule. A new rule must describe one evidenced
backend pathology with narrow inclusion and explicit exclusion conditions.

## Built-in rule 1: tetracoordinate P(V) building

Descriptor:

```text
rule_id  = tetracoordinate_pentavalent_phosphorus_build
version  = 1.0.0
stage    = pre_build
priority = 100
```

For atom $p$, let $Z_p$ be atomic number, $q_p$ formal charge, $h_p$ Open
Babel hybridization, $d_p$ graph degree, and $o_b$ the integer order of an
incident bond. The rule matches only when all of the following hold:

$$
Z_p=15,\quad q_p=0,\quad h_p=5,\quad d_p=4,
$$

$$
\sum_{b\sim p}o_b=5,
$$

and the four incident bonds comprise exactly:

- one non-aromatic double bond from P to O or S; and
- three non-aromatic single bonds.

The action emits the temporary change

$$
h_p:5\rightarrow3.
$$

The bridge applies this only while `OBBuilder.Build()` runs and restores
$h_p=5$ in a `finally` block. Formal charges, bond orders, aromatic flags, and
topology are not changed.

Explicit exclusions are:

- trivalent phosphorus;
- charged phosphonium;
- five-coordinate phosphoranes;
- charge-separated phosphoryl representations such as P$^+$--O$^-$;
- P=C and other double bonds not involving O or S;
- aromatic incident bonds; and
- atoms whose Open Babel hybridization is not 5.

The rule is a builder workaround. It does not assert that every matched P(V)
center is physically tetrahedral after optimization.

## Built-in rule 2: degenerate non-linear torsion preflight

Descriptor:

```text
rule_id  = degenerate_nonlinear_torsion
version  = 1.0.0
stage    = pre_forcefield_setup
priority = 100
```

This rule is planned only when `prepare_optimization(..., forcefield)` receives
`"UFF"`, case-insensitively.

For adjacent atoms $i-j-k$, define

$$
\mathbf{u}=\mathbf{x}_i-\mathbf{x}_j,\qquad
\mathbf{v}=\mathbf{x}_k-\mathbf{x}_j,
$$

$$
s(i,j,k)=
\frac{\lVert\mathbf{u}\times\mathbf{v}\rVert}
     {\lVert\mathbf{u}\rVert\lVert\mathbf{v}\rVert}
=|\sin\theta_{ijk}|.
$$

A candidate requires:

- center $j$ is not a metal;
- its Open Babel hybridization is at least 2;
- its graph degree is 3 or 4;
- both vectors have length greater than $10^{-12}$;
- $s(i,j,k)\le\epsilon_s$, where the default
  $\epsilon_s=10^{-6}$;
- at least one of $i$ or $k$ has a neighbor other than $j$, so the angle can
  occur in a proper four-atom torsion; and
- at least one side is a separable branch after removing its bond to $j$.

The smaller separable branch is selected; ties use the lower root atom index.
Candidates are ordered by $(s,i,k,\text{branch root})$ for deterministic
behavior.

The selected branch is rigidly rotated around $j$ by the default
$\alpha=10^{-3}$ radians. The rotation axis is derived deterministically from
the Cartesian basis vector least aligned with the branch direction. Rodrigues'
formula is used:

$$
\mathbf{r}'=\mathbf{r}\cos\alpha
+(\hat{\mathbf{a}}\times\mathbf{r})\sin\alpha
+\hat{\mathbf{a}}(\hat{\mathbf{a}}\cdot\mathbf{r})(1-\cos\alpha).
$$

Because the whole separable branch undergoes one rigid rotation around the
center, its internal geometry and bond lengths are preserved. Planning repeats
at a center until no candidate remains.

Explicit exclusions are:

- all non-UFF force fields;
- metal centers;
- centers with hybridization below 2;
- centers whose degree is not 3 or 4;
- genuinely non-degenerate angles;
- zero-length adjacent vectors;
- angles that cannot participate in a proper torsion; and
- ring-connected sides for which no branch can be separated without reaching
  the center again.

This rule does not change or clamp the UFF torsion derivative. It moves an
exactly singular starting geometry by a small deterministic amount and the
bridge then checks whether Open Babel reports finite energy and gradients.

## Public Python API

### Functions

| Function | Purpose |
|---|---|
| `available_rules(stage: Optional[RuleStage] = None) -> tuple[RuleDescriptor, ...]` | Return compiled rules in deterministic execution order, optionally filtered by stage |
| `build(obmol: ob.OBMol, *, builder: Optional[ob.OBBuilder] = None, stereo_warnings: Optional[bool] = None) -> BuildReport` | Plan temporary build mutations, invoke native `OBBuilder` once, and restore temporary hybridization metadata |
| `prepare_optimization(obmol: ob.OBMol, forcefield: str, *, singularity_threshold: float = 1.0e-6, repair_angle_radians: float = 1.0e-3) -> OptimizationPreparationReport` | Apply deterministic UFF coordinate preflight mutations before `Setup()`; other force fields are strict no-ops |
| `validate_forcefield_state(backend: ob.OBForceField, obmol: ob.OBMol) -> ForceFieldStateReport` | Evaluate energy with gradients and report whether both are finite |

### Public value types

All report classes are frozen dataclasses.

| Type | Fields / meaning |
|---|---|
| `RuleStage` | `PRE_BUILD`, `PRE_FORCEFIELD_SETUP` |
| `RuleDescriptor` | `rule_id`, `version`, `stage`, `priority` |
| `HybridizationChange` | zero-based `atom_index`, `before`, `after` |
| `CoordinateChange` | zero-based `atom_index`, three-component `before`, `after` coordinates in angstroms |
| `RuleApplication` | descriptor, target atom indices, optional metric, hybridization changes, coordinate changes |
| `RuleExecutionReport` | stage and ordered applications; `.applied` is true when applications are present |
| `BuildReport` | `succeeded` and rule execution report |
| `OptimizationPreparationReport` | force-field name and rule report; `.applied` mirrors the report |
| `ForceFieldStateReport` | energy in the backend's native unit, finite flags, zero-based non-finite-gradient atom indices; `.passed` requires finite energy and gradients |

## Native `_ob_rules` API

`_ob_rules` is an implementation module, not a stable end-user API. Its typed
surface is recorded in `_ob_rules.pyi`.

| Native symbol | Role |
|---|---|
| `AtomSnapshot(atomic_number, formal_charge, hybridization, is_metal)` | Immutable atom input |
| `BondSnapshot(begin, end, order, aromatic)` | Immutable zero-based bond input |
| `RuleStage` | Native lifecycle stage enum |
| `RuleDescriptor` | Registered rule identity |
| `HybridizationChange` | Planned hybridization mutation |
| `CoordinateChange` | Planned coordinate mutation |
| `RuleApplication` | One rule application and its evidence |
| `RulePlan` | Ordered applications for one stage |
| `available_rules(stage=None)` | Read the compiled registry |
| `plan_build(atoms, bonds)` | Validate a graph snapshot and execute PRE_BUILD rules |
| `plan_optimization(atoms, bonds, coordinates, singularity_threshold, repair_angle_radians)` | Validate a coordinate snapshot and execute PRE_FORCEFIELD_SETUP rules |
| `RuleApplicationLimitExceeded` | More than 256 applications were requested |

Native planners validate positive atomic numbers, non-negative
hybridizations, valid non-self bond indices, non-negative bond orders, matching
coordinate counts, and finite coordinates. Optimization thresholds must obey

$$
0\le\epsilon_s<1,\qquad 0<\alpha<\pi,\qquad
|\sin\alpha|>\epsilon_s.
$$

## Force-field integration points

The production integration is deliberately narrow:

- `forcefields/backend.py::_ob_build()` calls `obWrappers.build()` while the
  existing builder and force-field locks are held.
- `forcefields/backend.py::_setup_forcefield_backend()` calls
  `prepare_optimization()` before every native `Setup()`.
- If a preparation rule applied, the same setup helper calls
  `validate_forcefield_state()` and raises a structured setup error for a
  remaining non-finite state.

The setup helper is shared by `_single_ob_optimization()` and the stateful
`_OpenBabelOptimizer`; no public force-field function has a wrapper-specific
parameter.

## Failure semantics

- Failure to import `_ob_rules` raises `ImportError` with an instruction to
  install a compatible wheel or rebuild Hotpot.
- Invalid native snapshots or numerical settings raise `ValueError`.
- More than 256 applications raises `RuleApplicationLimitExceeded`.
- A native builder returning `False` produces `BuildReport(succeeded=False)`;
  the force-field integration translates this to `ForceFieldError`.
- Temporary build hybridizations are restored even when native building raises.
- `prepare_optimization()` mutates matching coordinates in place. It does not
  promise standalone rollback. Production workflows operate on working
  molecules and retain their existing transactional commit behavior.
- Native `Setup()` failure remains `ForceFieldSetupError(stage="setup")`.
- A non-finite state after an applied preparation rule becomes
  `ForceFieldSetupError(stage="preflight-validation")`.
- An unmatched rule is not treated as an error or warning.

## Concurrency and compatibility

The C++ planner owns no Open Babel object and operates on a copied snapshot.
Registry access and planning are read-only after module initialization, and the
bindings release the GIL during native planning.

Open Babel operations themselves remain subject to Open Babel's process-local
state. Calls made through `hotpot.cheminfo.forcefields` retain the existing
builder and force-field locks. Direct users of `obWrappers.build()` must not
concurrently mutate the same `OBMol` or `OBBuilder`.

The package supports Hotpot's Python 3.9--3.14 range:

- Python 3.9 uses the project's Open Babel 3.1 compatibility worker;
- Python 3.10--3.14 use the current Open Babel 3.2 path;
- `_ob_rules` links only to Python/pybind11 and the C++ standard library, not to
  `libopenbabel`, so one rules source is used for both Open Babel ABIs; and
- the extension is still CPython-ABI-specific and must be built for every
  supported interpreter.

## Building

Install in editable mode and let setuptools build both pybind11 extensions:

```bash
$ python -m pip install -e .
```

For an explicit in-place development rebuild:

```bash
$ python setup.py build_ext --inplace --force
```

For distribution artifacts:

```bash
$ python -m build
```

The `_ob_rules` extension is declared in the repository root `setup.py` and
requires a C++17 compiler. A wheel must contain an extension matching its
target CPython ABI.

## Test evidence and limitations

Focused verification command:

```bash
$ python -m pytest -q -p no:cacheprovider \
    tests/test_cheminfo/obWrappers \
    tests/test_cheminfo/test_forcefield_integration.py
```

Observed on Python 3.11 with Open Babel 3.2.1 on 2026-09-28:

```text
36 passed in 24.71s
```

The tests cover native inclusion/exclusion boundaries, deterministic plans,
read-only records, registry ordering, one-call native delegation, temporary
metadata restoration, all P-containing structures in
`molecules/extractant/extractants.smi`, finite UFF gradients, non-UFF no-op
behavior, public force-field integration, multiprocessing, and thread-level
serialization.

The complete 187-extractant Eu workflow was also rerun with 16 workers and the
same seeds and force-field settings as the pre-wrapper baseline:

| Result | Baseline | Registered guards |
|---|---:|---:|
| Quality passed | 167 / 187 | 175 / 187 |
| Quality failed after CBond | 11 / 187 | 3 / 187 |
| CBond failed before force-field work | 9 / 187 | 9 / 187 |
| Non-finite-gradient cases | 9 / 187 | 0 / 187 |
| Wall time, 16 workers | 128.431 s | 138.753 s |

Eight formerly failing structures now pass and no formerly passing structure
fails. All nine P(V)-associated non-finite-gradient failures are removed. One
of those nine, case 54, now reaches a finite UFF result but remains a quality
failure because an atom is too close to Eu; it is not counted among the eight
new passes. Cases 61 and 109 retain their pre-existing geometric failures. The
aggregate force-field time increased by 150.097 s (7.70%); among the 161
non-P-containing cases that passed in both runs, the median increase was
0.708 s. This is the measured cost of the current portable SWIG snapshot and
planning boundary, not a zero-overhead abstraction.

Current limits:

- this is a targeted compatibility layer, not a general molecular repair
  engine;
- the registry is compile-time extensible and read-only from Python;
- only PRE_BUILD and PRE_FORCEFIELD_SETUP stages exist;
- finite-state validation runs after setup only when a preparation rule was
  applied;
- the torsion rule relies on graph paths as a conservative proxy because Open
  Babel does not expose its active UFF torsion-term list through this API;
- no UFF formula or parameter is changed; and
- metal placement and coordination-collapse failures, including benchmark case
  109, remain the responsibility of the force-field coordination workflow.
