## 1. 总目标与范围

化学业务事实第一。完成 [Plan20 主实施计划](fact_rule_architecture_implementation_plan.md) 的全部剩余获批范围，并在同一事实载体、规则、操作与适配器架构内完成 [Plan12](../12_xtb_workflow/README.md) 的功能要求、必要科学执行及交付；不建立平行实现。保留完整架构和业务范围，按下述优先级推进，不以当前检查点、测试数量或工具链完成度替代总体目标。

Hotpot 为化学家提供灵活建模具体环境的方法，在声明的表示约定、方法假设、后端能力及适用域内追求避免明确错误（Not Error），并服务于高通量筛选、后续计算、模型输入和进一步精化。研究者保留环境、方法与结果的选择及解释权；Hotpot 不宣称唯一的实验或理论真相，也不预设唯一结构、偏电荷、配位数、键长或 MCA 值。

先完成 Stage0–12 主范围验收并形成真实已验证的 Git 基线 `B_exp`，再分别开展 Stage13A 的私有芳香/Kekulé 协议定义及 `D_exp` 提交、Stage13B 的接入及 `I_exp` 提交。实验不得替代前序工作、提前放行主范围或改写其验收结论，也不自动推广至其他领域。既有算法按获批范围迁移；科学算法变化必须明确纳入范围并单独归因。Plan21 的 MetalCluster 运行实现保持其独立范围，Plan20 仅承担既定设计登记。

## 3. 科学语义、围栏与批次行为

用户输入事实、Hotpot 规则结果和 toolkit 投影分别归属。规则、fallback、sanitization、芳香识别、Kekulé 赋值和适配器不得静默重写权威输入。只有同一 subject、权威 fact slot、scope、lifecycle 和表示约定下不可兼容的陈述才构成冲突。合法芳香/Kekulé 表达可为等价投影；共价键数、操作性价态、配位数和共价贡献分别解释。toolkit 的不支持或有损投影按适配器边界报告，不据此重定义 Hotpot 事实或宣称化学不可能。

命名硬规则在其声明域内拒绝受影响的输入、候选、请求或结果，并保留确切规则与诊断。电荷、电子数及自旋合法性依所选方法和后端定义；非有限能量不得冒充有效能量。缺失或错误的必要单位、映射、归属、schema 或事务完整性，使局部结果不可用，即使其数值有限。碰撞、穿环、高能等几何或能量问题须给出适用域、条件、参考和阈值；获批的操作性拒绝不等于所有研究语境下的普适不可能。

非硬规则报告可能问题。有限、可归属且完整的观察默认保留并返回，finding 不得静默擦除、替换或“修复”它。finding 使用稳定的领域 code，指出确切现象、受影响对象及必要的读数、参考、阈值、单位或原因；没有发现解释或控制相关问题时保持安静。

finding 内容与 warning、局部失败、break 或批次停止策略独立。非硬 finding 默认报告并继续；用户可按具体 code 将其提升为操作、样本或批次 break，这属于预期控制。只有客观无法继续，或共享身份、归属、映射、状态、事务及基础设施受损而使后续结果不可信时，才升级为意外的更大范围终止。每个实际规则、gate、适配器边界与工作流阶段须在其所属记录中明确并检验：

`finding code｜适用域与触发条件｜是否仍有定义良好的值｜默认行为｜允许的逐code break范围｜提交/回退后果`

独立样本失败应隔离、归因并保留在稳定分母中。失败、重试、修复和 fallback 均保留原始尝试及影响解释的科学意义变化，保留可取得的最后有限观察；这些观察不把失败改记为成功。既有获批硬规则与完整性保护不得静默回退，启发式观察的变化须按方法、规则、输入和版本解释。

## 4. 架构与公开结果边界

每项持久事实只有一个权威 owner。规则只读，返回实际不可变或已隔离缓冲的提案、观察或结果；小型命名 operation 负责完整验证、原子提交及失败回滚。依赖失效有限且归属明确，不返回旧值冒充当前值；已返回历史结果保持其内容。迁移须追踪真实写者、读者、适配器和回滚路径，在同一连贯修改中移除旧实现、冗余真相和无批准的兼容路线。保留普通化学对象 API、高效批量访问及唯一拓扑基础，不创建通用规则注册、第二套缓存或重复事实系统。

普通成功 API 返回请求的值；请求本身可以是候选集、分布或轨迹，已有成功命令也可按合约返回 `None`。不额外增加统一 status/result envelope、质量等级、admissibility 标签或虚构置信分数。必要内部诊断、来源绑定和生命周期元数据留在其计算、控制、持久化或报告 owner，不因此扩充普通输出。公开路径、签名、权限、返回语义和 schema 的具体变化仍按既有审阅边界处理，本目标不隐含批准新 API。

结果的归因与解释依据 Hotpot 版本、命名方法/模型、有效参数（含默认值）及相关执行条件。对随机或并行浮点计算，记录条件并检验其实际复现程度，不将这些信息表述为数学上唯一决定输出。执行前已知输入不在普通结果中重复；只有执行时新发现、调用者原本未知且影响解释或控制的信息才需要额外报告。

方法实现、表示约定、假设和适用限度写入版本化配套文档；科学支持写入基准验证报告，必要时引用文献。缺少所需语料、计算、依赖或机器时明确列出未取得的证据、待执行内容，结果留空。科学可信程度由方法、适用域、实现和实测证据共同形成，不用统一标签替代；方法自带且有明确校准与验证的 uncertainty 可按其已审合约表达。

## 5. 验证标准与业务可追溯性

每个有边界的业务切片先写清期望事实、允许差异、明确拒绝条件和必要测试，再实施并解释结果。验证覆盖实际受影响业务、技术不变量与必要科学行为；已声明的反应、质子化或电子转移按该操作允许的变化判断，不能套用“任何操作都不得改变原子/H/电荷”的假不变量。

新旧版本不必全面相同。确定性且确有无修改或无损运输要求的事实、映射、schema、顺序及权限继续作精确检查；化学表示按明确原子映射和约定判断等价，计算结果按方法、单位、尺度、精度与收敛性选择预先说明的容差，随机或近似方法采用与任务有关的重复、分布或稳定性证据。不把历史成功数、文本/对象顺序或逐位相等当作通用科学标准，也不在看到结果后放宽标准来吞掉真实错误。

SHA256 等摘要用于代码、输入和产物的来源归因与传输完整性，不等于化学正确性。运行边界的必要来源检查应足以解释证据，不为每个样本或小探针反复扫描全环境或重建放行体系。

验证必须能追溯“业务要求 → 实际调用与案例 → 证据 → 结论及局限”。复用现有验证地图及[执行单元业务映射](functional_707_business_mapping.md)，按实际风险补齐缺口；执行组合数和历史通过数都不是目标或化学覆盖率。CP311 的真实核心流程先于广泛版本、反射和归档矩阵，不设某轮清单、比较器、fresh 归档及 profiler 串联的通用前置链。

校验器自身故障应单独保留和归因，可绕开故障工具，使用可信、可解释的直接业务证据，后续修复或重构该工具。绕过工具不能绕过业务标准；无可信证据的业务仍为未验证，退出码或封装完成不冒充业务通过。已有有效证据在来源、输入、方法和受影响范围仍适用时复用；新增修改、失败或未解风险有理由时才重跑受影响部分，保留失败、回归、未执行项和分母。

## 6. 性能、版本与可用性交付

执行顺序为 **化学语义正确性 > 可接受性能 > 全版本适配**。先确保 Python3.11 的核心业务与交付路径，其他 Python3.10–3.14 版本随后集中适配。版本、平台和依赖的支持声明须对应真实证据，未测或延期不能写成通过或已支持。

初始设计选择高效方法，注意批量处理、局部复用、快照/转换成本和资源界限，不要求每个 stage 先完成全面优化。主 agent 可依据用途、工作量、可完成性、耗时与资源证据接受可解释的退化并记录理由，再推进下一阶段。约5倍变慢是用户给出的可接受情境示例，不设统一的5.000倍阈值；旧 parity、少数轻微退化额度或每阶段全版本矩阵不再充当通用硬前置，也不要求逐项另获用户批准才能接受可解释退化。OOM、资源无界增长或代表性大批次不能完成仍是业务可靠性问题，须处理其受影响路径。

性能证据使用可比语义工作量、方法、输入与资源条件，保留原始样本、失败尝试、实际工作和不确定性；不能靠删除案例、改分母、少做计算、抑制问题或换后端制造收益。全面优化与扩展兼容可后补，当前吞吐/资源局限照实报告。私有 native 候选或特定机器上的修复证据，仅支持其实际测试范围，不能冒充普通安装已交付的依赖修复。

## 7. 推进、记录与完成口径

主 agent（root）对代码、集成和实验验证边界负责，可据直接证据调整已授权范围内的设计、阶段内顺序、诊断、warning/break、修复/fallback、测试和证据路线。调整须保留获批总体范围、公开边界、科学约束、数据完整性和本目标规定的验收方向，不得为增加成功而隐藏失败或缩减业务。改变这些已批准边界的提案须明确提出，不能混作内部路线调整。

每个阶段或独立子阶段进入前，全文阅读主计划、当前修订与规范性配套记录，对齐实际源码、产物、已获证据和前序门；实质修订或架构/科学路线变化后重新对齐。遇到矛盾，在最小连贯检查点修正过时正文并记录依据及验证影响，不能机械沿用与本目标冲突的性能、全版本或矩阵前置。对齐服务于下一业务切片，不扩张为反复全环境调查。

按“有边界的业务修改 + 必要验证 + 局限”形成小型可审阅提交并正常 push，保留他人及无关工作。维护 [implementation_log.md](implementation_log.md) 的 append-only 记录，写明实际命令、源码/产物身份、覆盖范围、pass/fail/skip、科学观察、性能与资源、失败、决策、API/owner 影响、待办及 Git 提交；不为每个准备或调度动作另造细碎 checkpoint。

限定范围可用、阶段完成、主范围验收和完整目标完成分别说明。延期兼容、可选功能及外部依赖问题须记明真实状态、影响、后续负责人和补验条件；必要业务缺证据继续保持未验证，不将延期项计为通过。既有明确可延期范围沿其已批准边界处置，其他剩余工作不得借优先级调整静默消失。

完成须以完整 Plan20 架构、集成 Plan12 业务、按本目标修订后的适用最终验证、必要科学报告、真实交付、日志和报告相互一致为依据。检查范围按业务风险与实际支持承诺确定，不把旧全矩阵或性能 parity 原样重新塞回完成条件。CP311 局部通过不能代表完整计划完成，缺失执行不能充作通过。主范围最终报告须与最终代码、API、删除/合并记录、科学与性能证据、延期项及已验证 Git 交付一致；达到前述主范围要求后才形成 `B_exp`，Stage13A/B 另行验证和报告。
