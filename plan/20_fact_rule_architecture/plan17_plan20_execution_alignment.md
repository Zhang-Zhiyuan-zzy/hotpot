# Plan17 / Plan20 实施顺序与验收口径对齐

修订日期：2026-10-28。Plan20 Stage0 已核对项目状态并选定执行顺序；
生产重构尚未开始。本次路线决策不设立新增公开属性、方法、类型、字段或 ABI。

本文件与 [Plan20 主规划](fact_rule_architecture_implementation_plan.md)、
[化学类型公开接口一致协议](chemical_type_interface_contract.md)及
[Plan17 原生构象扩展](../17_rdkit_wrapper/organic_native_conformer_implementation_plan.md)
共同定义后续顺序与接口边界。历史实施报告保留其当时的计数和判定，不能作为本轮
科学结果必须一致的要求。本文件中的命令、记录名称和阶段编号均为实施
交付约定，不是新设立的运行时公开 API。

## 1. 已选顺序与原因

本轮 Stage0 选择 **先 Plan20，后 Plan17 的最小 MCA 原生构象批次 `17-MCA`**。
`17-MCA` 延至 `F20` 之后独立实施；`B20` 与 `F20` 固定使用当前唯一的
Python-RDKit MCA 构象算法。Stage1 先实际采集基线，再开始生产重构。

当前 MCA 路线执行 ETKDGv3 后的 MMFF94/UFF 优化；当前原生 rdWrapper
只有 ETKDG。既有 [256 分子评估](../17_rdkit_wrapper/mca_conformer_engine_assessment.md)
记录了预测差异与无明显加速，不能把直接替换成原生 ETKDG 视作等价去重。
Stage0 核查了现有 `AImodels/mca/conformer.py` 与原生 `sampler.cpp`：前者复用
可用三维坐标，否则执行单构象 ETKDGv3、MMFF/UFF；后者尚无原生力场优化及
相应结果传输。`17-MCA` 最小闭环未完成，因此采用计划已允许的延期路线。
Plan20 只迁移当前算法及调用边界，后端替换在 `F20` 后单独留证。

不必等待 Plan17 全部后续工作：多构象聚类、普通有机 `build3d()` 默认切换、
普通有机构建与优化默认切换均独立交付，不进入 MCA / Plan20 的关键路径。
MCA 一次只请求一个构象，聚类不是它的能力前置。
普通有机默认切换等改变实际工作量的后续批次，应在 B20 之前独立完成并
重新测量基线，或安排在 F20 之后；不得夹入 B20/F20 之间混淆重构效果。

| 路线 | 主要代价 | 本次安排 |
|---|---|---|
| Plan17 最小 MCA 前置，再 Plan20 | 前置需补原生优化并完成公开接口审阅 | 本轮不采用；原生闭环尚未完成 |
| 先 Plan20，后 Plan17 | 当前 MCA 路线先搬迁，再作独立后端切换 | 本轮 Stage0 已选；B20/F20 固定当前唯一算法，17-MCA 延至 F20 之后 |
| Plan17 全部后续工作完成后再 Plan20 | 等待聚类、普通有机默认切换和全部扩展矩阵 | 不作为依赖，避免无关工作扩大关键路径 |
| 在 Plan20 迁移提交内直接切换 MCA 后端 | 科学变化、数据结构与包路径变化混在同一比较中 | 不采用 |

“先 Plan20”是本轮明确选定的实施顺序，不是安装后可选择的
old/new profile，也不在生产代码保留两个构象实现。任何时点只有一条
获准的生产 MCA 构象路线。

## 2. 17-MCA 的边界与交付（F20 之后）

最小原生闭环沿用标识 `17-MCA`。本轮在 `F20` 之后按以下先后顺序完成：

1. **17-MCA-0：审阅与基线。** 提交公开 API / ABI 完整差异表供负责人
   审阅；在首次原生扩展或切换前，重新记录当前 MCA 科学状态与效率。
   所有新增公开类型、参数、记录字段和 C/C++ 声明未经审阅不得实施。
2. **17-MCA-1：能力补齐。** 在现有单一原生核心中实现 H 展开/原始行映射、
   单构象 `EmbedMolecule`、AUTO MMFF94/UFF、200 次迭代与显式种子42。
   保持现有无优化调用的行为和 standalone 边界；不借此增加聚类或普通
   有机默认工作流变化。
3. **17-MCA-2：结果传输。** 通过获准的 C / C++ / Python 契约返回实际力场、
   执行状态、坐标、能量及诊断；共享字段选择式缓冲区。不得重复声明分子
   事实 schema；不得以默认零值或替代坐标掩盖缺失。
4. **17-MCA-3：MCA 接入。** DTO / feature worker 使用原生路线，保留当前
   Python-RDKit 特征构造器；保持当前模型、位点识别、资源调度及 O0 选择。
   已有可用三维坐标输入的复用、缺失几何时的生成条件和失败报告行为
   必须先表征，不能只比较从 SMILES 开始的路径。
5. **17-MCA-4：独立报告与切换。** 完成组件技术检查、安装包检查、MCA
   科学状态报告和配对性能报告。解释科学差异，取得所需接口及默认切换
   审阅后，在一个可审查提交中替换生产实现并删除被替代的提案执行体。
   保留历史记录，不保留隐藏运行时回退。

原生优化产生非有限能量、未收敛或几何监控异常时，记录实际执行状态、
恢复轨迹、最后可用帧与缺失原因。算法无法产生可传输坐标属于执行结果；
几何和能量监控读数本身不构成科学真伪或结构准入判决。

批次完成清单包含：确切提交/树摘要、获准接口表、构建/依赖身份、实际
命令与机器分配、测试与科学报告、原始计时样本、模型身份、每例输入与
输出记录，以及删除的实现清单。完成不要求历史科学输出逐项一致。

## 3. 两条基线分开保留

| 记录 | 采集时间 | 用途 |
|---|---|---|
| `B17` | 17-MCA 第一项代码变更前 | 比较现有 Python-RDKit 路线与原生优化路线 |
| `F17` | 17-MCA 接入完成后 | 记录后端替换的科学状态和独立性能变化 |
| `B20` | 后端选择已冻结、Plan20 首项生产重构前 | 全项目架构/事实存储重构的实际效率与行为基线 |
| `F20` | Plan20 最终候选提交 | 与 B20 比较架构重构本身的影响 |

本轮已选路线中，`B20` 使用尚未切换的当前 Python-RDKit MCA 路线，`F20`
也必须使用该路线；Plan17 在 `F20` 之后另行采集 `B17/F17`。`B20` 的确切
提交和测量由 Stage1 实际记录，目前待执行；`0a4b0ee` 仅保留为规划审计锚点。

若以后在另一轮实施中选择 Plan17-first，须先完成 `F17`，再重新采集该轮
`B20`。任何路线变更都须先同步两个实施文档和依赖记录，不能追溯替换已冻结
的比较边界。不能用原生替换的速度收益抵消事实存储或身份校验
引入的性能损失，也不能把不同后端、不同科学规则版本直接混成一个性能比值。

## 4. 科学状态报告

187 是既有来源集合的历史规模，182 是某一版本规则下导出的合格子集规模。
每次运行分别记录来源内容摘要、规则/模型版本、资格判定与逐例纳入原因；
对同一来源按当前规则重新推导子集，不把 182 固化为成功数量或永久资格。
来源变化必须生成新身份，不能覆盖旧 manifest。

科学运行交付可复查的逐例报告，而不是一个布尔验收值：

- 输入身份、实际资格结果、规则/模型/后端身份、实际种子；
- 执行完成、失败、未产生输出或缺失证据的阶段与原因；
- 几何监控读数、阈值及其版本、能量/力/梯度、非有限值与恢复信息；
- 坐标与最后可用帧、监控不确定性、运行时间和资源；
- 当前及历史统计、配对可比子集、仅当前/仅历史案例及差异解释。

几何/能量 gates 作为带版本的监控器输出观测，不自动判别科学正确性。
旧结果不是 ground truth。与过去一致、达到固定成功率或没有任何数值
漂移，均不是本轮科学报告完成条件。数值差异仍需定位来源，不能用高
相关系数掩盖局部较大差异；但差异本身也不自动宣告科学退步。

O0 报告使用种子42/43/44，并明确是逐例实际种子还是批次根种子；若 runner
对根种子加案例索引，必须输出每例实际值。报告保留全部尝试，不能用
后续成功重试覆盖先前记录。MCA 配对报告保持同输入/种子/模型条件，记录
位点、预测、坐标和资源差异；科学规则更新作为单独可归因的变更记录。

技术测试仍检查所有权、shape、原始行映射、事务完整性、序列化、接口、
资源路由及实际算法调用等不变量。把科学监控改成报告不表示取消这些
技术断言。API 返回的执行状态也不等同于科学上“有效/无效”的结论。

## 5. 效率基线与全局标准

B17 和 B20 均在对应第一项代码变更前运行实际基准。用相同内容摘要、
规则/后端、构建模式、依赖、CPU 亲和性/线程、进程模型、GPU 分配进行
配对测量。共享节点的功能观察不能代替受控性能基线。

Plan20 主规划第12节为两计划共同采用的效率记录与全局标准来源：覆盖
运行路径、测试运行、冷/热启动、单项/批量读写、逐原子结果投影、原生
跨界、推理与内存。既记录原始样本、median/MAD 和置信区间，也记录
冻结权重的全局汇总，禁止用挑选工作负载掩盖退化。

目标为整体至少持平，并预期整体更快；允许 ×1 附近的测量波动及极少数
已逐项解释的轻微变慢。各项损益、异常数量、总体比值和不确定性都必须
公开。具体操作阈值由主规划统一定义，Plan17 不另保留“所有路线可慢2%”
的冲突标准。能力扩展中新增加的聚类、优化等工作与旧路线工作量不同，
单独给出增量成本，不能伪装成相同工作负载的速度回归。

## 6. 化学类型公开接口的共同协议与审阅边界

两计划采用[化学类型公开接口一致协议](chemical_type_interface_contract.md)：事实
唯一归属、接口与事实/计算映射、读写权限、完整变更、按需重算、缓冲所有权及生命
周期，适用于全部 Hotpot 化学类型的构造器、属性、方法、集合、返回对象和转换。
范围包括 Molecule、Atom、Bond、Crystal、构象/分子集合、派生视图、科学结果和
公开运输值；standalone wrapper 保留其已批准组件契约，adapter 在边界遵守协议。

统一的是语义声明与实施约束。各类型按角色选取存储和可变性；Atom 列式事实表是
具体实现。视图与不可变结果不能因字段可单独赋值就获得 setter；多输入共同决定
事实时使用完整操作。依赖状态归权威 owner，独立值不强加分子身份或 dirty 状态，
已返回历史结果不随活动分子改写。内部 schema 增列不自动发布任何同名公开属性。

Plan17 扩展第4节列出的新增 Python 类型、现有类型新增字段、C ABI 字段/函数及
C++ 声明仍是待审提案，不因本轮规划修订自动获准。最小批次只提交 MCA 所需
子集；聚类专属字段在聚类交付时另列，不能顺手进入该批次发布。统一协议不改变
既有 standalone API/ABI、字段序、单位与结果保证。

Plan20 的字段声明、依赖状态和提交控制均为私有实现。任何化学类型新增、删除、
改名、公开路径、签名、读写权限、返回类型或生命周期变化，都须在待审清单中
列出确切入口、owner/依赖、旧入口去向及验证依据，再经负责人逐项审阅。
Atom 的 A1–A13 是该清单中的具体候选，不能作为其他类型自动增设接口的授权。
MetalCluster 及 `Molecule.metal_clusters -> list[MetalCluster]` 是用户指定的未来目标；
Plan20 仅登记类型关联，具体注册与超原子工作归
[Plan21](../21_metal_cluster/metal_cluster_implementation_plan.md)，不增加 Plan17/20 的运行前置。

## 7. 阶段责任与完成证据

| 责任 | Plan17 | Plan20 |
|---|---|---|
| 原生 MMFF/UFF 能力、单构象调用和 MCA 默认切换 | F20 之后由 17-MCA 独立完成 | B20/F20 保持当前 Python-RDKit 算法，只迁移调用边界 |
| 多构象聚类、普通有机默认切换 | 独立后续批次 | 不作为硬前置 |
| 化学类型公开接口、事实存储、按需重算与对象归并 | 提供组件契约与消费者证据；保持 standalone 边界 | 建立跨类型声明、按角色迁移；Atom 表为具体实现 |
| 公共 wrapper 类型/ABI | 保持单一已审契约 | 不为内部命名统一破坏 standalone 边界 |
| 科学与效率记录 | B17/F17 | B20/F20，含全局运行与测试效率 |
| 包路径与构建迁移 | F20 后消费最终 ownership tree，standalone 路径保持 | 按最终 ownership tree 成套迁移 |

文档交付完成后，实施者先冻结选定顺序、待审接口结论和实际基线提交。
没有测量文件时，状态必须明确标注“待执行”，不得宣称效率基线已记录。
