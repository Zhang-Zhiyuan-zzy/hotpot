# Hotpot CLI 设计规范

本文档规定 Hotpot 新增或大幅重构命令行接口时应遵循的设计风格和基本契约。它补充
`skills/development.md`，不得放宽其中关于架构、科学语义、失败处理、验证和交付的要求。

文中 **MUST（必须）**、**SHOULD（应当）** 和 **MAY（可以）** 是规范性用语。已有公开命令如与本文
不一致，应先确认兼容性和迁移影响；遗留实现不是新命令的设计模板。

## 1. 总体定位

Hotpot CLI 是同时面向人类用户和 LLM/自动化代理的公共接口，也是 Python API 的薄命令行适配层。
它应当具备以下特征：

1. 对人清晰：命令可发现、帮助准确、名称可读、错误可行动、科学含义明确；
2. 对 LLM 可预测：语法规则统一、参数无歧义、输出结构稳定、无需交互式猜测；
3. 对管线友好：能够安全使用重定向、标准输入输出和 shell 管道，便于嵌入复杂命令行；
4. 对科学计算忠实：不隐藏适用域、单位、索引、后端选择、资源边界或失败状态；
5. 对程序稳定：退出状态、stdout、stderr 和输出格式构成可测试的公共契约。

CLI 的默认形态采用 Unix 风格和 Git 风格子命令：

```text
hotpot <command> <required-inputs> [options]
```

新命令 MUST 使用项目现有的 `argparse` 体系，除非已有明确批准的全局迁移方案。不得为单个命令引入
另一套平行 CLI 框架。

## 2. 命令与参数设计

### 2.1 命名与布局

- 子命令和长选项 MUST 使用小写 kebab-case，例如 `all-structures`、`--input-format` 和
  `--batch-size`。解析后的 Python 属性使用 snake_case。
- 必需且稳定的核心输入 SHOULD 使用位置参数；配置、输出路径和可选行为使用命名选项。
- 位置参数的 `metavar` SHOULD 表达输入类型，例如 `SMILES/FILE`、`MODEL_DIR`。
- 常用且含义公认的选项 MAY 提供短形式，例如 `-o/--output`。文档和自动化示例 SHOULD 优先展示
  无歧义的长选项。
- 有限取值 MUST 使用 `choices` 或等价的显式枚举；数值参数 MUST 声明正确的解析类型。
- 帮助文本 MUST 说明默认值、单位、适用条件以及选项间的重要关系。
- 未实现的选项不得出现在公共 CLI；预留参数若因兼容性必须存在，必须明确说明当前不生效。
- 不得依靠选项名的模糊匹配、静默纠错或未记录的别名。未知参数必须失败。

### 2.2 语义选择

- 不同科学解释不得用含混 Boolean 隐式切换；应使用具名模式、profile 或枚举。
- Boolean flag 只适合启用或禁用语义单一的附加行为，例如输出详情或生成图片。
- 显式请求的设备、模型或后端必须严格执行；只有明确命名为 `auto` 的模式允许自动选择。
- 可能组合爆炸或消耗大量资源的操作必须提供显式、文档化的上限，不得静默截断。
- 随机或非确定性流程 SHOULD 提供 seed 选项，并说明该 seed 控制的范围。

### 2.3 输入消歧

- CLI MUST 复用共享 reader、converter 和规范化入口，不得自行复制格式识别或化学解析逻辑。
- 同一位置参数同时接受路径和直接值时，必须记录判定顺序，并提供 `--input-format` 或其他明确的
  消歧方式。
- 支持多记录输入的命令 SHOULD 接受多记录文件；适合批处理的命令 SHOULD 支持多个位置输入。
- 对天然可流式处理的命令，标准输入 `-` SHOULD 表示 stdin。若命令不支持 stdin，帮助和文档不得
  暗示其可用于输入管线。
- SMILES 等包含 shell 元字符的输入必须在示例中正确引用。

## 3. 架构与代码组织

### 3.1 薄入口

- 根入口只负责创建解析器、注册子命令、解析参数、配置全局基础设施和分发。
- CLI 只可承担输入适配、API 调用、结果格式化和交付，不得实现 reader、converter、模型、site
  detection、科学筛选或绘图算法。
- 科学计算路径必须由 Python API 决定。增加或移除展示形式不得改变计算结果。
- 输入转换、runtime、科学 API、结果对象、格式化和文件写入 SHOULD 保持可辨识的分层。
- 可选重依赖和命令专属依赖 SHOULD 延迟导入，避免一个不相关子命令因未安装的可选依赖而无法启动。

### 3.2 命令模块形态

新命令 SHOULD 延续以下可组合结构：

```python
def add_arguments(parser: argparse.ArgumentParser) -> None: ...
def run(args: argparse.Namespace) -> int: ...
def build_parser() -> argparse.ArgumentParser: ...
def main(argv: list[str] | None = None) -> int: ...
```

- `add_arguments()` 供顶层 `hotpot` 入口注册子命令。
- `run()` 执行一次命令并返回退出状态。
- `build_parser()` 和 `main(argv)` 使模块能够独立调用和测试。
- 结果格式化 SHOULD 尽量写成接收领域结果、返回字符串或结构化记录的纯函数。
- 完全相同的文档 action、输出交付或其他 CLI 基础能力应抽取为共享 helper；契约不同的行为不得为减少
  表面重复而强行合并。

## 4. stdout、stderr 与管线契约

### 4.1 流的职责

- stdout MUST 只包含命令承诺的结果数据，且内容必须稳定、可重定向、可被下游程序消费。
- 日志、警告、进度、诊断和性能信息 MUST 写入 stderr。
- 正常结果中不得混入 `Done`、欢迎语、调试对象、进度条或其他装饰性文本。
- 数据 stdout MUST NOT 包含 ANSI 颜色或依赖终端宽度的动态控制序列。`--help`、`--doc` 等纯人类展示
  可在 TTY 中渲染，但不得改变正常数据流。
- 每次成功输出 SHOULD 以换行结束，以便与其他 Unix 工具组合。

### 4.2 重定向与输出文件

- `-o/--output FILE` 写入的逻辑 payload MUST 与默认 stdout payload 相同；使用 `-o` 时 stdout 必须为空。
- 文本输出 MUST 使用 UTF-8。
- 若支持 `-o -`，它必须明确表示 stdout。
- 输出顺序、字段名、分隔符、数值精度、缺失值和末尾换行均属于格式契约，不得无说明改变。
- 若输出不再符合某种文件格式，例如在 SMILES 后附加排名或诊断详情，文档必须明确建议使用合适的
  文本扩展名或结构化格式。

### 4.3 管线与机器可读格式

- 命令不得默认发起 `input()`、确认提示或其他交互。交互能力如确有必要，必须由显式
  `--interactive` 启用，并不得用于自动化默认路径。
- 非平凡的多记录或嵌套结果 SHOULD 提供稳定的机器可读格式，例如 TSV、JSON 或 JSON Lines；格式选择
  SHOULD 使用类似 `--format` 的显式选项。
- 流式多记录输出 SHOULD 优先采用一条记录一行的格式，以便 `grep`、`awk`、`jq`、`xargs` 等工具处理。
- JSON 输出必须是标准 JSON，不得包含 `NaN` 或 `Infinity`。键名、单位、索引基准和 schema/version
  语义必须明确。
- 能够流式执行的命令 SHOULD 逐步消费输入并产生输出；必须批处理时，应说明批次、缓存和内存行为。
- 下游正常提前关闭管道所产生的 `BrokenPipeError` MAY 按 Unix 惯例安静结束，但不得借此吞掉计算或
  数据错误。

## 5. 科学结果表达

- 单位 MUST 出现在字段名、表头、图例或结构化 schema 中。
- Hotpot 内部原子索引为 0-based。面向人的输出 MAY 使用 1-based，但命令必须明确声明采用哪一种基准。
- 原始模型分数、阈值判定、相对权重、校准概率、热力学量等概念必须使用不同且准确的名称。
- 模型原始预测不得伪装成经适用域验证的结果；域外结果必须拒绝或显式标记。
- 空结果、部分结果、科学质量不合格、执行失败和资源上限中止必须是可区分状态。
- 多结果输出的排序规则必须确定且有文档；性能优化不得改变结果顺序。

## 6. 错误、退出状态与诊断

- 成功命令返回 `0`；参数错误和执行失败必须返回非零状态。
- 参数语法错误由 `argparse` 或统一解析层报告，不得静默采用猜测值。
- 未知程序异常必须原样传播，不得转成成功、空结果、零值或自动 fallback。
- 已知领域错误只有在保留原始失败证据并维持非零退出状态时，才可以在顶层转成更简洁、可行动的
  stderr 信息。
- 明确的 `auto` 后端回退必须有名称、文档和测试；显式后端失败不得自动改用其他后端。
- “没有符合条件的结果”是否成功由命令的领域契约决定；无论采用何种状态，都必须有明确输出或错误，
  并由测试固定。
- 错误信息 SHOULD 指出失败对象、约束或可采取的下一步，但不得伪造科学结论。

## 7. 人类与 LLM 的可发现性

- 每个命令 MUST 提供准确、简洁且无需运行任务即可访问的 `--help`。
- 复杂命令 SHOULD 提供随包发布的详细 Markdown 文档，并可通过 `--doc` 查看。
- `--help` 和 `--doc` 必须在缺少业务位置参数时仍可正常退出。
- 文档必须包含命令 synopsis、输入类型、默认值、单位、索引、输出格式、退出/失败语义、适用域、资源
  限制和可复制示例。
- 示例 SHOULD 同时覆盖直接调用、`-o`、shell 重定向，以及命令确实支持时的 stdin/stdout 管线。
- 示例输出必须来自已验证运行或明确标为示意，不得把编造数值写成真实模型结果。
- 文档应使用完整、稳定的长选项和明确引号，使人类与 LLM 无需依赖上下文推断隐含状态。

## 8. 验证要求

新增或改变 CLI 行为时，测试深度必须与风险相称，并至少考虑：

1. parser 的必需参数、默认值、`choices` 和互斥关系；
2. `main(argv)` 与顶层 `hotpot <command>` 的分发和退出状态；
3. 稳定格式的精确输出，包括字段、顺序、精度和换行；
4. stdout 与 stderr 分离，以及 `-o` 与 stdout payload 等价；
5. 多输入、多记录、合法空结果和失败路径；
6. stdin/stdout 管线和机器可读格式（若支持）；
7. `--help`、`--doc` 在无业务输入时可用；
8. 真实 reader、converter、backend 或模型路径的集成闭环；
9. entry point、package data 或依赖变化后的 wheel 外部 smoke test。

Golden 输出必须人工审查。不得用当前实现自动覆盖 expectation 来掩盖非预期的 CLI 契约变化。

## 9. 打包、兼容性与迁移

- 公共入口统一为 `hotpot`，子命令通过项目 entry point 暴露。
- 新增运行时依赖、entry point 或 `--doc` 等 package data 时，必须同步检查 `pyproject.toml`、
  `setup.py` 和 `MANIFEST.in`。
- 已发布命令名、选项名、退出状态和稳定输出格式属于公共兼容面。破坏性修改必须有证据、迁移说明和
  必要的 deprecation 周期。
- 无依据的旧别名、兼容 wrapper 和两套活跃实现不得长期保留。
- 新实现接管后必须全仓搜索调用者、文档和测试，清理被取代路径。

## 10. 新命令检查清单

- [ ] 命令同时便于人类发现和 LLM 无歧义调用。
- [ ] 可安全使用重定向，并在适用时支持 stdin/stdout 管线。
- [ ] stdout 只有稳定结果，stderr 承载日志、警告和诊断。
- [ ] 参数、默认值、单位、索引、适用域和资源上限明确。
- [ ] CLI 复用 Python API 和共享输入/绘图能力，没有复制科学逻辑。
- [ ] 无默认交互、静默 fallback、吞异常、静默截断或伪成功结果。
- [ ] 返回码能可靠区分成功与失败，空结果语义明确。
- [ ] `--help`、详细文档、示例和打包内容同步。
- [ ] parser、格式、管线、失败、集成和安装后入口经过风险相称的测试。
